- 🐛 `[FIX]` **The prompt's "now" anchor and its conversation-turn headers render in DIFFERENT timezones, so the model computes elapsed time wrong by the UTC offset** (user report 2026-09-14 via the owner: "it'll say something happened an hour ago when it happened about 20 seconds ago, or it'll say something was last week but it was actually an hour ago"). NOT a model defect — diagnosed from a real debug payload for one request, not from code reading. In that payload the volatile-prefix anchor rendered `<datetime>Monday, September 14, 2026 at 07:05 PM UTC</datetime>` while the conversation turn headers rendered `[<name> — 2026-09-14 (Mon) 14:44]` … `15:02`. The request's own `meta.timestamp` was `2026-09-14T19:05:33.914Z`, which is `15:05` in America/New_York — so the headers are EDT and the anchor is UTC. **The last turn was 4 minutes before the request; the model reads it as 244.** Mechanism: `PromptBuilder.buildVolatilePrefix` calls `formatFullDateTime(new Date(), context.userTimezone)` and honors the user's configured zone (UTC for this user), while the turn headers go through `formatAbsoluteTimestamp`/`formatPromptTimestamp` with NO timezone argument, so `resolveTimezone(undefined)` falls back to `APP_SETTINGS.TIMEZONE` = `America/New_York` (`packages/common-types/src/constants/service.ts`). Only the anchor carries a tz label, so the two are not reconcilable from the prompt text. Fix shape: thread `userTimezone` through to every prompt-facing time formatter (`formatRelativeTime` and `formatPromptTimestamp` already ACCEPT an optional timezone and are simply called without one — e.g. `langchainConverter.ts` calls `formatRelativeTime(createdAt)`), or render every prompt timestamp in one zone and label it. The formatter inventory to sweep is enumerated in `services/ai-worker/src/utils/promptTimestampShapes.ts`. Acceptance: a debug payload for one request shows the anchor and the newest turn header in the same zone, and their difference equal to the real elapsed time. Note the second-order effect: a user whose timezone happens to BE `America/New_York` sees no bug, which is why this survived.
