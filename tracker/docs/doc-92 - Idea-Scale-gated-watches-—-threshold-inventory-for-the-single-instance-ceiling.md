### Idea: Scale-gated watches — threshold inventory for the single-instance ceiling

_Focus: the 21 places where a load, cardinality, or replica ceiling is already written into the code — collected side by side, with the number, so a future "we are scaling" session has a checklist instead of a search._

## Why one doc

Every member's promote-when is a load, cardinality, or replica condition a single-owner instance does not produce, and **none of them can fire without measurement we do not have**. doc-7's batch log already recorded this ruling once, for two of these exact rows: _"The HttpPersonalityLoader pair (64/65) was evaluated and NOT pulled: both tasks say 'fine at current scale' with unfired runtime promote-conditions — building them would be premature optimization."_

**Cross-link: doc-16 (Theme: Production Observability) is the enabling theme.** doc-16's premise is that "we log what happened but have ~no aggregated performance signal" — and none of the 21 triggers below can be OBSERVED until that changes. Scheduling doc-16 is what makes this doc actionable; until then every row here is correctly unfired.

**Selection cost: the highest of any shape in the 2026-09-04 pass, and worth stating plainly.** These are exactly the rows a future scaling session would want as a checklist, so a title list would be strictly worse than 21 scattered rows. Written as an inventory with the numbers side by side, it is *more* useful than the rows were: the thresholds become comparable, and it becomes obvious which ceiling is nearest.

**Two rows are not really latency deferrals and should be read differently.** TASK-210 is a **correctness** gap past its bound (memories are left live, not merely slow), and TASK-103 is a **completed negative probe** kept as a re-probe trigger rather than pending work.
