## Workspace-root coverage (the original item)

**Why.** `pnpm-workspace.yaml` declares four workspace packages: `packages/*`, `services/*`, `scripts`, and `tests`. Three guards hardcode only the first two as their `ROOTS`:

- `packages/tooling/src/dev/check-build-scripts.ts`
- `packages/tooling/src/dev/check-no-export-star.ts`
- `packages/tooling/src/dev/check-dockerfile-dist.ts`

Nothing is unguarded **today** — verified at filing: `tests/package.json` has an empty `scripts` object, and `scripts/package.json` has no `build` key (it does run `tsc --noEmit` for typecheck, and its source is not part of knip's dead-export surface). So this is a coverage gap with no live instance, not a defect.

It matters because of what the guards are FOR. `guard:build-scripts` exists specifically to catch a *new* package silently reintroducing turbo cache poisoning; `scripts/` already invokes `tsc` and is exactly the shape that could grow `"build": "tsc"` later, with no CI signal. A guard against silent reintroduction that cannot see two of the four places a package can appear has a hole in its own premise.

**Why it is a sweep and not a one-line fix.** Widening one guard's `ROOTS` array leaves the three inconsistent, and the next guard added copies whichever one its author read. The fix is a single shared source of truth.

**Fix shape.** A small helper in `packages/tooling/src/dev/` that reads the `packages:` globs out of `pnpm-workspace.yaml` once and expands them to concrete directories; the three guards above consume it instead of their local `ROOTS`. Then a guard's coverage follows the workspace definition automatically — adding a fifth root to `pnpm-workspace.yaml` cannot silently leave the guards behind.

Two things to decide while building it, not before:

- Whether `tests/` should be in scope for every guard or only some (its package is a test-fixture host, so an `export *` there masks nothing knip audits).
- Whether the helper parses the YAML or shells out to `pnpm ls -r --depth -1 --json`. Parsing is dependency-free but has to handle the glob forms; the CLI form is authoritative but adds a subprocess to a fast sync check.

**Acceptance.** One helper, three call sites, no remaining hardcoded root pair in `packages/tooling/src/dev/`; each guard's existing tests still green; and a test proving a package under a non-`packages`/`services` root is actually scanned.

**Members so far.**

1. `check-build-scripts.ts` — surfaced by the PR #2062 review (the guard shipped with the two-root scope; its known limitation is stated in the PR body and the module docstring).
2. `check-no-export-star.ts` — same hardcoded pair.
3. `check-dockerfile-dist.ts` — same hardcoded pair.
4. `TASK-178` — `findServiceFiles` in `packages/tooling/src/test/audit-unified.ts` hardcodes six `<pkg>/src` directories, so every new package escapes the coverage ratchet until someone remembers to add it. Same rot, one layer down: it needs `<pkg>/src` rather than the package root, and keeps its own Prisma-usage filter, but it would consume the same expanded root list. Filed separately and older than this doc; listed here so the sweep does not leave it behind.

**Related.** `TASK-489` (archived as a duplicate of `TASK-32`) asked for the guard over "every **workspace** package" — broader than the two-root scope that actually shipped in #2062. This doc owns that remaining breadth, so the ask is not lost with the duplicate.

## Static-guard blind spots (absorbed 2026-09-04)

**Why one doc.** This file already argues the case for one instance — _"Widening one guard's `ROOTS` array leaves the three inconsistent, and the next guard added copies whichever one its author read."_ The generalization is that every row below is **our own guard or scanner with a known hole in its own premise**, and every one was deferred at a review-round cap rather than dismissed on merit. `TASK-571` was already half-owned here (`check-build-scripts.ts` is listed by name in § Members so far), which is what made the widening the honest move rather than a new doc.

**Selection cost**: an `area:tooling` query loses thirteen rows — but they were never picked individually, because none is worth a slot alone. The doc is the batch, and it is genuinely one PR's worth of "make each guard say what it cannot see."

- **TASK-571 — `check-build-scripts` guard: two workspace roots unscanned, and fail-open on its own read errors** (filed 2026-08, was state:ready size:S). Two defects: (1) `ROOTS = ['packages', 'services']` while `pnpm-workspace.yaml` declares four globs including `scripts` and `tests`, and turbo runs `build` across all workspace packages — so a future `"build": "tsc"` in either is exactly the new-package-reintroduces-the-class failure this guard exists for; the same blind spot exists in #2064's `discoverServiceDirs` at lower stakes. (2) `checkPackageJson` returns null on an unreadable or invalid `package.json`, and a `readdirSync` failure skips the root entirely — the guard is silent about its own errors, with permission-error-shaped silent skips as the practical exposure. Fix shape: derive roots from `pnpm-workspace.yaml` (the shared helper this doc proposes), and make guard-internal read errors a finding. Trigger/cost: verified latent — neither root has a build script today. Evidence 2026-09-04: `grep -n "^const ROOTS" packages/tooling/src/dev/check-build-scripts.ts` → `['packages', 'services']`; `cat pnpm-workspace.yaml` → also lists `scripts` and `tests`.
- **TASK-141 — `PATH_TOKEN_PATTERN` over-matches inside URLs** (filed 2026-06, was state:observable size:S). A GitHub deep link containing a `/packages/`- or `/services/`-shaped path segment is extracted as if it were a repo path, producing false-positive reminders. Fix shape: exclude matches preceded by a `://`-bearing prefix (lookbehind, or pre-strip URLs from the row before tokenizing). **RETARGET (2026-09-04)**: the task text says `deferred.md`, which no longer exists as the reference source — `check-deferred-refs.ts` now scans **tracker task prose** (`tracker/tasks/`), and the tool's own JSDoc notes the name is a holdover. The over-match risk applies unchanged to the new source. Trigger/cost: promote when a tracker task gains a GitHub deep link to a monorepo file, or a false-positive reminder is observed. Evidence 2026-09-04: `sed -n '1,60p' packages/tooling/src/dev/check-deferred-refs.ts` → now scans `tracker/tasks/` text via `PATH_TOKEN_PATTERN`; `grep -rlE "github\.com/[^ )]*\/(packages|services)\/" tracker/tasks/` → **0** matches today.
- **TASK-228 — `guard:prompt-tags` `STRING_LITERALS` regex mis-bounds nested template literals** (filed 2026-07, was state:dependent size:S). A template literal containing a nested backtick template inside `${...}` terminates the outer match at the first inner backtick, so the guard could misparse rather than fail loudly. Fix shape: a brace-aware template scan, or accept the redundancy explicitly. Trigger/cost: no nested-template formatter exists today, and `TAG_PROPERTY`/`HELPER_TAG_ARG` would likely still catch the tag — promote when a formatter is refactored to nested templates. Evidence 2026-09-04: `sed -n '163p' packages/tooling/src/dev/check-prompt-tags.ts` → `STRING_LITERALS` unchanged, still single-backtick-bounded.
- **TASK-310 — `button-order-danger-last` walker misses variable `setStyle` args** (filed 2026-07, was state:observable size:S). When the LAST-executed `.setStyle(...)` in a chain takes a non-literal argument (ternary or variable) while an EARLIER call used a literal `ButtonStyle.Danger`, the walk skips the unresolvable outer call and classifies from the stale overridden literal — so the runtime style is actually unknown. Fix shape: on the first-visited (last-executed) `setStyle` hit, if the argument is non-literal, mark the whole chain unresolvable (return null) instead of falling through, plus a pin test. Three lines when the trigger fires. Trigger/cost: promote when the double-`setStyle`-with-dynamic-last shape appears, or the rule produces a confusing false positive. Evidence 2026-09-04: `git grep -B2 -A2 "\.setStyle(" services/bot-client/src` → spot-checked `db-sync.ts`, `servers.ts`, `browse.ts`, `view.ts`; every site is a single literal `.setStyle()` call, no double-call dynamic-last shape found.
- **TASK-467 — `guard:claude-content-refs` skips `.claude/hooks` and `.husky`** (filed 2026-08, was state:ready size:S). The guard validates that command references in `.claude` content resolve to registered ops commands, but its own output says "Checking 24 rule/skill files" — it covers `.claude/rules` and `.claude/skills` only. Hook scripts are not scanned, so a renamed ops command leaves a hook printing a dead invocation with nothing failing. **Not hypothetical for hooks specifically**: `pr-merge-review-check.sh` prints `release:finalize` and `release:premigrate`, `pr-monitor-reminder.sh` embeds the whole `gh:ci-gate` invocation, and the husky hooks call several `pnpm ops` commands directly. Fix shape: extend the guard's file set to `.claude/hooks/*.sh` (and probably `.husky/*`), reusing the existing extraction — shell files will need the extractor to tolerate commands inside heredocs and printf strings; confirm whether the staleness-threshold half applies or is skipped for hooks, which carry no `lastUpdated` frontmatter. Acceptance: renaming a registered ops command that a hook references fails `guard:claude-content-refs`, pinned by a canary. **RETARGET (2026-09-04)**: the file is `packages/tooling/src/audits/check-claude-content-refs.ts`, **not** `src/dev/`. Note also the disposition on the finding that surfaced it: the release-sequence prose DUPLICATION between the hook, the git-workflow skill, and `05-tooling.md` is **correct as-is and needs no guard** — a reminder pointing at a procedure is not the byte-for-byte copy-paste failure mode `guard:monitor-command` exists for. Evidence 2026-09-04: `grep -n "\.claude/hooks\|\.husky" packages/tooling/src/audits/check-claude-content-refs.ts` → 0 matches, and the guard is scoped to rules/skills only.
- **TASK-519 — Coercible flags whose names are not id-shaped are invisible to the guard** (filed 2026-08, was state:ready size:M). `snowflakeFlagArgv.test.ts` catches id-shaped flags by naming heuristic, plus a hand-maintained `EXTRA_GUARDED_FLAGS` list for the ones no heuristic can see — which is the same remembering-based mechanism the guard was written to replace. Fix shape: make detection mechanical rather than name-based — scan each action body for parsed-option reads of any declared flag and require `rawOptionValue` for any whose value is later used as a string id, or invert the guard so every declared flag must be either read via `rawOptionValue` or annotated as safe. Weigh against false-positive noise on genuinely numeric flags (`--lines`, `--limit`, `--drain-timeout`). Acceptance: adding a coercible flag under a non-id name fails CI without anyone editing an allowlist, **or** the allowlist approach is recorded as the deliberate end state with its reasoning. Evidence 2026-09-04: `git grep -n "EXTRA_GUARDED_FLAGS" packages/tooling/src` → still a literal array in `snowflakeFlagArgv.test.ts`, no mechanical detection added.
- **TASK-525 — `RUNNER_STAGE_PATTERN` misses a flag-bearing `FROM`** (filed 2026-08, was state:observable size:S). `guard:dockerfile-dist` anchors on `/^\s*FROM\s+\S+\s+AS\s+runner\s*$/i`, requiring a SINGLE token between `FROM` and `AS`, so a multi-arch stage written `FROM --platform=$BUILDPLATFORM node:25-slim AS runner` does not match — `classifyRunnerStage` returns unnamed and the guard emits a runner-anchor finding on an otherwise-correct Dockerfile. Fix shape: widen the pattern to tolerate leading flags on the image reference while keeping the end-of-line anchor that stops runner-debug from re-anchoring; update the disclosed-limitation JSDoc and flip the characterization test from documenting the miss to asserting the match. Trigger/cost: not a defect today, and the limitation is disclosed in the pattern JSDoc and pinned by a characterization test; the trigger arrives on its own as a red CI run naming the service, which is why it is `observable` rather than `ready`. Evidence 2026-09-04: `grep -rn "FROM.*AS runner\|--platform" services/*/Dockerfile` → 4 runner stages, all plain `FROM node:25-slim AS runner` / `FROM nginx:alpine AS runner`, none flag-bearing.
- **TASK-549 — `find-dead-files` prints "No dead files found" when grep is wholly broken** (filed 2026-08, was state:ready size:S). `hasNonTestImporters` answers true (assume imported) for any grep failure that is not exit 1 — the safe direction for a single call, since an unknown must never promote a file onto a deletion list. But if grep is broken for the WHOLE run (missing binary, ENOENT, a bad `searchDir`), every candidate answers true, `findDeadFiles` returns zero, and the command prints its cheerful all-clear. Verification never ran and nothing says so. Fix shape: track how many importer greps failed during a run; if all failed, or the count crosses an obvious threshold, print a warning that importer verification did not run and suppress the all-clear. Trigger/cost: **this is the mirror of the bug #2072 fixed** — there a failed check produced a confident wrong POSITIVE (a live file called dead); here a wholly failed run produces a confident wrong NEGATIVE (a clean bill of health nobody earned). Same root shape: a failure answering as data. Evidence 2026-09-04: `grep -n "No dead files found" packages/tooling/src/dev/find-dead-files.ts` → line 161, printed whenever `deadFiles.length === 0`, with no failure-count gate.
- **TASK-572 — Snowflake raw-argv guard is file-granular; the UUID exemption is a text sniff** (filed 2026-08, was state:ready size:S). `snowflakeFlagArgv.test.ts` enforces `source.includes(rawOptionValue(...))` per FILE, so a file declaring the same id flag in two subcommands with only one raw read passes (the collector dedups duplicate declarations) — no current instance, but the guard reports safety it does not fully check. Separately, the UUID exemption is `/uuid/i` over a 300-char description window, so any description merely mentioning uuid exempts the flag even if it also accepts snowflakes. Fix shape: per-declaration (command + flag) enforcement, and an exemption keyed on an explicit annotation instead of a text sniff. Trigger/cost: confirmed latent at filing (2026-08-12 review, tooling L4). Evidence 2026-09-04: `grep -n "rawOptionValue\|includes(" packages/tooling/src/commands/snowflakeFlagArgv.test.ts` → `source.includes(...)`, whole-file scope, unchanged.
- **TASK-606 — `classifyNoMatch` under-reports a stray `--` and a bad flag beside a bad command** (filed 2026-08, was state:ready size:S). Two gaps in one function (`packages/tooling/src/utils/unknown-command.ts`), both probe-confirmed: **(a)** `pnpm ops -- foo` prints help and exits 0, because cac routes positionals after the literal `--` into the options object under the `"--"` key rather than into args, and `findUnknownFlags` deliberately skips that key since it is present on every invocation — so a mistyped `pnpm ops -- db:status` silently succeeds. **(b)** `pnpm ops --bogus-flag no-such-command` reports only the unknown command; the flag typo goes unreported because `findUnknownFlags` is consulted only inside the no-command-name branch. Fix shape (a): with no command name and no unrecognized flags, treat a NON-EMPTY `options["--"]` array as an unknown-command-shaped error naming its first element — and pin both `pnpm ops` and `pnpm ops --`, since an empty-vs-absent mistake here re-breaks the bare invocation. Fix shape (b): compute unknown flags regardless of branch and fold them into the message when both apply, keeping the single-problem messages byte-identical. Trigger/cost: third and fourth paths in the family TASK-454/TASK-457 opened; neither is urgent — (b) still fails loudly with a correct if incomplete message. Evidence 2026-09-04: `sed -n '78,90p' packages/tooling/src/utils/unknown-command.ts` → no `options['--']` check; `grep -n "'--'" ...` → referenced only inside `findUnknownFlags`'s own filter.
- **TASK-627 — premigrate scan: quoted-identifier folding and the `ALTER COLUMN TYPE` bound** (filed 2026-08, was state:ready size:S). Two narrow fail-direction gaps in the destructive-shape scan, found after the comment-stripping walker landed. **(1)** `normalizeTableRef` lowercases quoted identifiers, but Postgres quoted identifiers are case-sensitive — a migration creating `"Foo"` then destructively targeting a pre-existing `"foo"` would be wrongly exempted (**fail-open**); unreachable via Prisma-generated migrations, which are always lowercase snake_case, and live only for hand-written SQL with case-colliding names. Fix: fold case for UNQUOTED refs only, preserve case inside double quotes, red-proof with a `"Foo"`/`"foo"` pair. **(2)** The `ALTER COLUMN TYPE` pattern bounds its span with `[^;]*`, written when a statement could never contain a semicolon; post-walker a dollar-quoted body keeps its internal semicolons inside one statement, so dynamic `ALTER COLUMN ... TYPE` text straddling such a semicolon silently fails to match (**false negative**, against the over-warning-is-safe stance). Decide: drop the bound and accept over-flagged spans across dollar bodies, or scope it — then pin. Acceptance: both gaps closed with red-proofed tests, or explicitly catalogued in the `splitSqlStatements` docstring residual list **with the fail direction stated**. Evidence 2026-09-04: `grep -n "normalizeTableRef\|ALTER COLUMN" packages/tooling/src/release/migration-scan.ts` → lines 74/93/107, pattern and function both matching the description verbatim.
- **TASK-672 — prefix-diff terminal sanitizer misses C1 controls 0x80–0x9F** (filed 2026-08, was state:ready size:S). `oneLine` in `packages/tooling/src/cache/prefix-diff.ts` neutralises C0 controls and DEL (`code < 0x20 || code === 0x7f`) so verbatim prompt text — persona bios, pasted Discord messages — cannot garble the terminal it prints to, but it does not cover the C1 range. On a legacy 8-bit-clean terminal `0x9B` is an alternate CSI introducer: a second escape-sequence entry point that never passes through the already-handled ESC (`0x1B`) case. Fix shape: extend the predicate to `(code >= 0x80 && code <= 0x9f)` and add the case to the existing test pinning CR and ESC — one line plus one assertion, negative-controlled the way the sibling assertions were (mutate the predicate away, confirm the test reddens). Trigger/cost: a real if small gap rather than a nit, because the function has an **explicit written threat model** naming CR and ESC, so leaving C1 out makes that model non-exhaustive rather than merely incomplete; real-world exposure is low, since modern UTF-8 emulators do not act on 8-bit C1. Deferred at PR #2146 round 6 with both remaining items marked optional and non-blocking. **Second, cosmetic item from the same review, folded in and NOT worth its own task**: a window boundary can split a UTF-16 surrogate pair, since offsets are code-unit-wise, leaving a lone surrogate that renders as a replacement glyph — no crash, no effect on the divergence math; fix it here only if it ever surprises someone. Evidence 2026-09-04: `grep -n "0x7f\|0x80\|code < 0x20" packages/tooling/src/cache/prefix-diff.ts` → line 185, predicate unchanged.
- **TASK-876 — `classifyLines` closes a fence on any same-character run, against CommonMark** (filed 2026-09, was state:ready size:S). `packages/tooling/src/dev/check-readme-classes.ts` closes a fence with `match?.[1].startsWith(fenceChar)`, comparing the delimiter CHARACTER only, so a three-backtick run closes a four-backtick fence where the spec keeps it as interior text. Fix shape, **already measured during the round-2 work and recorded rather than lost**: store the whole opening run — `fenceChar = match[1]` in place of `match[1][0]` — and the equal-or-greater-length rule falls out of the existing `startsWith` comparison; every other fence test stayed green under that mutation, and the only fixture needing an update is the documented-limitation one, which flips to asserting the CommonMark-correct interior classification. **Second divergence, same closing branch, folded in from round 3**: a closing delimiter carrying TRAILING CONTENT still closes the fence, though CommonMark allows only trailing whitespace on a closer (an info string is permitted on the opener alone) — the branch matches on `FENCE_DELIMITER`, which anchors on the leading run and ignores what follows, so both divergences share one code path and should be fixed in one pass. Round 3 also asked whether `tag` on a closing-delimiter line reflects the OPENING fence's info string: **it does, and correctly** — the closing branch pushes the carried tag and never recomputes it. That half is correct by design and is explicitly NOT part of this task; it is recorded so the next reader does not re-derive it. Trigger/cost: no live impact — the real README has zero tilde fences and zero four-plus-backtick fences — which is why it was documented rather than fixed in PR #2315. Evidence 2026-09-04: `grep -n "fenceChar" packages/tooling/src/dev/check-readme-classes.ts` → line 71 `fenceChar = match[1][0]`, line 76 comparing via character-only `startsWith`.
