### Idea: Silent-degradation deferrals — the triggering change per member

_Focus: five deferrals whose trigger degrades something silently, so the author of the triggering change gets no signal and the diff that creates the hazard never surfaces it._

## Why one doc

These are the complement of the admission-bar "do it now" class, and the reason that class needs a boundary. In an ordinary third-instance deferral the person adding the Nth thing sees the existing N−1 in the diff they are writing, so no filed row is needed. In each row below the trigger's author gets **no signal**: a cache goes stale, a type guard stops guarding, a test stub stops asserting. "The diff that surfaces it" never surfaces it, so these cannot be admission-barred — and each is far too small to hold its own pool slot.

Selection cost is real but small: each names a specific future PR. The doc only earns its keep if every bullet names the **triggering change**, not just the fix — otherwise it inherits exactly the reachability problem it exists to avoid. Recommend `dev:deferred-refs` be pointed at this doc specifically (doc-7 Phase 3 already proposes pointing it at `tracker/docs/`).

## Members

- **TASK-47 — Vision cache invalidation when VisionConfigResolver gets a cache** (filed 2026-06, was state:dependent size:S). **Triggering change**: `VisionConfigResolver` being wired into `services/ai-worker/src/cacheInvalidation.ts`. Fix shape: add `invalidateUserVisionConfig` to `LlmConfigCacheInvalidationService` and call it from the vision write/clear paths in `model-override.ts` when `isVision`. Trigger/cost: silent because the shipped user-vision-default/override handlers (S2b/#1379) call only `invalidateUserLlmConfig`, scoped `kind:'text'` — the moment a vision cache exists it serves stale config with nothing failing. Evidence 2026-09-04: `git grep -n "LlmConfigResolver" -- services/ai-worker/src/cacheInvalidation.ts` → present (positive control); `git grep -rln "VisionConfigResolver" -- services/ai-worker/src` → only `VisionProcessor.ts` comments, never `cacheInvalidation.ts`.
- **TASK-363 — Wire cache invalidation for the description prompt if an admin edit path ships** (filed 2026-07, was state:dependent size:S). **Triggering change**: any write path that mutates a `system_prompts` row's CONTENT — an admin UI, an ops command, or a seed/bootstrap that updates rather than creates. Fix shape: subscribe `DescriptionPromptService` to the same Redis pub/sub channel pattern the other invalidation services use, publishing on the admin write path; `refresh()` is already public and single-flighted, so the subscriber is a one-liner. Trigger/cost: silent because the service polls the `isDefault` row on a TTL — until the TTL lapses ai-worker keeps framing image descriptions with the OLD prompt, and every description written in that window is cached and reused by other personalities. Evidence 2026-09-04: `git grep -ln "systemPrompt.update\|systemPrompt.upsert" services/api-gateway/src` → no results; only a `findFirst` read exists, in `admin/createPersonality.ts`. Recorded framing (#1873 round-4): the omission is currently intentional, not a gap.
- **TASK-425 — Deduped quote path: guard type disagreement between ProcessedAttachment and the attachment row** (filed 2026-08, was state:dependent size:S). **Triggering change**: a SECOND producer emitting `AttachmentType.File` entries into `preprocessedReferenceAttachments` — `DependencyStep` forwarding File stubs, or video processing per doc-59. Fix shape: at the correlation site in `buildDedupedAttachments`, when `hit.type` and `classifyAttachment(att)` disagree, prefer identity-only rendering and log a warn — or assert the invariant in the producer. Trigger/cost: silent because the correlation is a bare URL match with no type-agreement check, so a File stub description would render under an `<image>` tag as if it were paid vision output. Evidence 2026-09-04: `git grep -n "AttachmentType.File" services/ai-worker/src/jobs/handlers/pipeline/steps/DependencyStep.ts` → no results; `ReferencedMessageFormatter.ts:164-183` read directly — still a bare URL match, no type check.
- **TASK-138 — handleExpandField tests stub config as `{}`** (filed 2026-06, was state:dependent size:S). **Triggering change**: `handleExpandField` starting to READ config properties. Fix shape: replace the `{}` stub with a real (ideally `satisfies`-typed) `EnvConfig` fixture in the same diff that makes the handler read config. Trigger/cost: silent because the stubbed `{}` skips coverage of the new paths while the tests keep passing green. Evidence 2026-09-04: reader read `view.ts` `handleExpandField` (its `config` is passed straight through) and `api.ts` `fetchCharacter` (signature still `_config: EnvConfig`, unused in the body) — **narrowing note**: the call site has already lost its underscore prefix without the promote-when actually firing, so the underscore is no longer a reliable tell for this row.
- **TASK-102 — MessageContextBuilder.cachedBotSuffix: promote the pre-login note to a hard invariant** (filed 2026-05, was state:dependent size:S). **Triggering change**: an explicit `Client.isReady()` (or equivalent gateway-ready) assertion landing at the entry point of bot-client startup or the message-handler pipeline. Fix shape: ~5 LOC — drop the `cachedBotSuffix === null` guard and reach `client.user.tag` directly with a non-null assertion, turning the post-login assumption into an enforced invariant. Trigger/cost: silent because the field freezes at `''` if `fetchExtendedContext` ever runs pre-login; unreachable today only because extended context is driven by message events that fire post-`ready`, and nothing asserts that. Evidence 2026-09-04: `git grep -n "isReady()"` across `handlers/`, `index.ts`, `startup.ts` → no matches, with `cachedBotSuffix` itself matching as the positive control.
