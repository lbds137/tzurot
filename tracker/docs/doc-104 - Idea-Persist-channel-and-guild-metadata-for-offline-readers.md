## Why

Offline consumers cannot name a channel. `conversation_history` rows carry only `channel_id` and `guild_id`; channel, category, thread, and server names are resolved live from Discord on the request path (bot-client fetches them per message; ai-worker reads them from the envelope's `knownChannelEnvironments` map — `packages/common-types/src/utils/crossChannelEnvironment.ts` header comment) and never persisted. Three readers already pay for that:

- the recent-days digest sweep (doc-97 Phase 4, slice 1b) runs off the request path and can only say "in DMs" / "in server channel A" — a recorded deviation from the design's D3 ("in #general");
- the cross-channel feed falls back to `unknown-server` / `unknown-channel` whenever the envelope lacks a channel (`buildFallbackEnvironment`);
- TASK-668: forwarded quotes carry no origin channel even though the resolver fetched it.

Owner direction (2026-09-17): persist channel names and other useful guild metadata, as a separate task, handled in an intelligent way — not an ad-hoc column.

## Shape to scope (not decided)

Mirror the `UserGuildInfo` precedent (`prisma/schema.prisma` `model UserGuildInfo`; written by bot-client through `POST /internal/guild-member-info` — `services/api-gateway/src/routes/internal/guildMemberInfoRecord.ts` — and cleared by `guildMemberInfoRemove.ts` on the gateway's remove event):

- a `discord_channels` table keyed by channel id: guild id, guild name, category name, channel name, channel type, topic, thread name + parent id, `last_seen_at`; NOT sync-tracked (environment-local cache of Discord state, regenerated by use — same class as `EXCLUDED_TABLES` entries);
- written by bot-client on the request path where it already holds the resolved `DiscordEnvironment` (one fire-and-forget internal call, debounced per channel — e.g. skip when `last_seen_at` is within the hour — so a busy channel does not write a row per message);
- kept honest by Discord events bot-client already receives: `channelUpdate` refreshes, `channelDelete` / `threadDelete` / `guildDelete` remove;
- read by the three consumers above; the digest input builder swaps its per-generation letter labels for the persisted name when present and keeps the letter fallback when absent.

Questions the scoping pass answers: retention (rows for channels the bot left — tie to `guildDelete`, or age out with the last history row?); whether topic belongs (it is user-authored text in a system prompt: the same `escapeXml` path `current_location` uses today); whether guild-level metadata (name, icon, member count) deserves its own row or rides on the channel row; and whether this ALSO closes TASK-668's origin channel with the same read.

## Promote when

The digest renders on prod and the owner reads a digest whose "in server channel A" attribution is not enough — or TASK-668 is picked up, since both need the same table.
