_Focus: when messages targeting an active character or activated channel arrive while a generation for that channel is already in flight, coalesce the pending messages into ONE follow-up generation instead of one LLM round-trip per message._

Owner report (2026-08-09, verbatim): "if multiple user messages targeting an active character or activated channel in Tzurot land while Tzurot is in the middle of generating replies for the given channel, I think we should maybe collapse pending messages so there are fewer round-trip calls to the LLM. I've run into this a lot where someone talks in a lot of short messages in an activated channel, which triggers multiple often repetitive outputs because right now we have it as one output per user message. I'm drawing inspiration from seeing how Claude Code queues user messages while the LLM is busy with something"

**Current behavior**: one generation job per triggering message. Rapid short messages (very common Discord chat style) produce multiple queued jobs, each seeing slightly more history, yielding repetitive near-duplicate replies and multiplied token spend.

**Owner refinement (2026-08-09): collapse stacks by USER ALTERNATION.** Only consecutive pending messages from the SAME author collapse — concatenated with line breaks (or whatever renders best) into one logical user message, because the target is a typing style (many rapid short messages = one thought). A message from a different user breaks the stack: never over-collapse across authors, so the LLM never loses sight of who is speaking and no user loses potential memory formation from their turns.

**Second owner note (same day): the alternation-stack vs a room-addressed reply is NOT settled as a binary.** The owner considered the "one reply addressing everyone" shape too; at pickup, run a council pass on the design space looking for a third option — some hybrid/blend (e.g. alternation-stacked prompt turns with a single reply that can address multiple stacks, or mode-switching on buffer composition). Design question, deferred to whenever this doc gets picked up.

**Scoping questions for build time**:

- **Where the coalescing seam lives.** Natural shape: key an "in-flight" marker on (channel, personality); while one generation runs, arriving trigger messages accumulate in a pending buffer instead of enqueuing jobs; when the in-flight job completes, one job per same-author run drains the buffer (a strict-alternation buffer may still produce multiple jobs — that is correct, per the refinement above). Candidate homes: bot-client (before enqueue — knows Discord arrival order, but multi-replica state needs Redis), api-gateway (queue layer — BullMQ job dedup/delay primitives live here), or ai-worker (at job start, absorb newer sibling jobs — riskiest for double-reply races).
- **Discord UX**: one reply addressing a same-author run — which message does the webhook reply anchor to (latest? none?).
- **Memory/history integrity**: the messages still land as separate history rows and separate memory-formation inputs per author; collapsing affects only how many GENERATION round-trips fire, never what gets recorded.
- **Correctness rails**: BullMQ retry/idempotency semantics for a drained buffer (spend-idempotency rule, `04-discord.md`); ordering guarantee that the buffer drains in arrival order; a cap so a flood coalesces into bounded prompt growth; interaction with the existing per-message dedup cache.
- **Scope boundary**: mentions/replies to a personality in non-activated channels may deserve the same treatment (same in-flight key) or may stay 1:1 — decide at scoping.

Related: `RedisDeduplicationCache` (existing per-message dedup), api-gateway `queue.ts` (job creation), conversation-history rows already store per-message turns so the coalesced prompt can render them faithfully.

**Owner ruling (2026-11-18, AskUserQuestion "Latest wins"), superseding the 08-09 same-author-stack refinement:** while a generation for a (channel, personality) is in flight, every queued-but-not-started reply job for that pair is dropped except the NEWEST; the in-flight one finishes. The newest job re-fetches channel history, so the skipped messages (with their authors) are in its prompt and it can answer the room in one reply. Trigger: prod 11-18 03:10, Lilith in an activated channel answered three short messages from two users within a minute with three long replies, and the overlapping calls also got zero z.ai cache hits (no caller could read a cache another had not finished writing). Check at build: whether a skipped message loses its own memory-formation input (formation must stay per message, never per reply). Timing (same AUQ): first unit of beta.247, not beta.246.

**Owner ruling (2026-11-18, AskUserQuestion "Activated chatter only"), confirming the user-visible semantics before build:** coalescing applies only to automatic replies in activated channels; an explicit @mention of the character or a Discord reply to one of its messages always gets its own answer. The surviving job replies to the NEWEST message, with the skipped messages (and their authors) in its prompt; skipped messages get no reply of their own. Memory stays per message: today long-term memory is stored once per generation as a (trigger message, reply) pair (`storeInteraction` in `services/ai-worker/src/services/ConversationalRAGService.ts`), so a dropped job would lose its message's memory; the build stores each skipped message as its own interaction for its author, paired with the combined reply.

**Correction (2026-11-18):** the semantics put to the owner said the surviving reply answers "as a reply to the newest message". Persona replies are not Discord replies: `WebhookManager.sendAsPersonality` (services/bot-client/src/utils/WebhookManager.ts) sends `{content, username, avatarURL, allowedMentions}` with no message reference, so every persona reply posts in-channel. Coalesced replies keep that; nothing about anchoring changes.

**Build grounding (2026-11-18, read of origin/develop):**
- Trigger kind exists in bot-client only: `SlotResolver.ts` `SlotSource` ('reply' | 'activation' | 'dm-session' | 'mention') and `ResolvedSlot.isAutoResponse`, passed through `MultiTagCoordinator.submitSlot` to `PersonalityChatManager.submitChatJob`. It is not on the wire (no `isAutoResponse` in api-gateway, ai-worker or the job schemas). DM sessions are also `isAutoResponse: true` (DMSessionProcessor → PersonalityMessageHandler); the ruling covers activated channels, so dm-session must be excluded explicitly.
- No state keyed on (channel, personality) anywhere; no code removes waiting BullMQ jobs. ai-worker runs one Worker at `WORKER_CONCURRENCY` 5 with no per-channel limit, so same-pair jobs run concurrently today (the 11-18 03:10 trigger).
- bot-client saves each trigger message as a user history row before calling generate (`PersonalityChatManager.ts` saveUserMessage), and the worker re-fetches history at job start (`ContextStep` → `ContextAssembler.assembleCore`), so a later job already sees earlier messages.
- Memory in production is deferred and written in the same job after generation (`GenerationStep` → `ragService.storeDeferredMemory`; `duplicateRetry.ts` always passes `skipMemoryStorage: true`).
- Proposed seam (engineering call, to verify at spec time): bot-client, before submit. Keep an in-flight marker per (channel, personality) for activation-sourced jobs; an activation trigger arriving while one is in flight is held (its user row is still saved) and replaces any older held one; when the in-flight job's result lands, submit the newest held trigger with the skipped triggers' message ids/content in a new payload field, and the worker stores one deferred-memory interaction per skipped message (author = that message's user) paired with the final reply. Holding before enqueue avoids cancelling BullMQ jobs. Open checks: bot-client replica count (in-memory state is safe only single-replica; JobTracker and ResponseOrderingService are already in-memory), failure path (the in-flight job errors → still drain the held trigger), and the per-user BYOK key and config of the skipped author vs the submitted one.

**Open checks answered (2026-11-18, read of 2056799ee; load-bearing rows re-grepped by the driver):**
- Replicas: prod bot-client `numReplicas: 1` (Railway service config) → an in-memory hold is safe.
- Path: every activated-channel trigger goes PersonalityTriggerProcessor → `resolveSlots` (source 'activation') → `MultiTagCoordinator.startFanOut` (N=1 included). `PersonalityMessageHandler` is DM-only (sole caller `DMSessionProcessor.ts:164`), so dm-session never reaches the activation path. `resolved.source` is in scope at `submitSlot`.
- No single run-once terminal hook: success reaches `MessageHandler.handleJobResult`, but multi-tag failures (`JobFailureListener` → `coordinator.handleJobResult`) and the safety timeout (`flushEntry` directly) bypass it; per-group completion is `flushEntry`. The hold therefore needs its OWN release deadline; the 40-min JobTracker orphan sweep cannot be the backstop.
- Release AFTER delivery, not on result: the assistant history row is written by bot-client after the webhook send (`SlotDeliveryService.persistDeliveredTurn`, `SlotDeliveryService.ts:153`), so a survivor submitted on result arrival would miss the reply just produced.
- The user row is saved INSIDE `submitChatJob` (`PersonalityChatManager.ts:177`, before `generate` at :194). Holding a trigger therefore needs the save split out so it runs at hold time; otherwise the skipped messages never reach history.
- Ordering: registration happens after `generate()` returns a jobId (multi-tag registers the group), so a never-submitted trigger leaves nothing registered.
- Attachments: image descriptions are written by ai-worker per trigger job (`visionDescriptionWriter` targeting `triggerMessageId`); a skipped message keeps only its placeholder text. Voice transcripts are made in bot-client and are already in the row text.
- Incognito: decided in ai-worker per job `userId` (`ConversationalRAGService.ts` `isIncognitoActive(context.userId, …)`) → must be evaluated per skipped author for their memory.
- Key/model: resolved per job from the trigger author (gateway `stampResolvedConfig` → `LlmConfigResolver.resolveConfig(userId, …)`; ai-worker `AuthStep`/`ApiKeyResolver` on `jobContext.userId`; guest mode can change the model). The survivor runs on the NEWEST author's key and model.

**Owner rulings (2026-11-18, AskUserQuestion):** (1) "Newest author pays": the combined reply runs on the newest message author's key and model settings. (2) "Never skip them": a trigger carrying an image or file attachment always gets its own job, as today; only plain-text and voice chatter coalesces.

**Spec decisions (driver's engineering calls, 2026-11-18):** the hold has its own short release deadline (the release fires on delivery or terminal failure, or when the deadline lapses, whichever comes first); the release fires after delivery so the survivor's history fetch sees the reply; the user-row save is split out of `submitChatJob` so it runs at hold time; incognito is evaluated per skipped author; the skipped list is capped; a restart drops held triggers (their user rows are already saved, so they stay in history unanswered); the payload field and worker memory side land with or before the bot-client hold, so develop never skips without per-message memory.

**Interpretation ruling (2026-11-18, AskUserQuestion "Stickers/embeds"):** the "never skip them" ruling covers ATTACHMENTS only — sticker-only messages and embed-image links (Tenor GIFs, pasted CDN images that arrive as embeds) keep holding like plain text; the holdability predicate deliberately does not read `message.embeds`. (Review round 5 proposed treating embed images as non-holdable; this interpretation was already on record, so the proposal was dismissed and the PR body states the attachment scoping.)

**SHIPPED (2026-11-19):** PR #2769 merged to develop as 75ce58061 — one squashed commit (+4021/−239, 30 files), 8 worker rounds across 7 claude-review rounds, final verdict "no blocking issues". Shape as ruled above, with these reviewed deviations: mention/reply/dm slots bypass holds AND open no cycle (a mention generation is invisible to the hold — activated chatter coalesces independently of it); a failed survivor submission promotes the newest skipped trigger instead of dropping it (round-3 design decision, owner-affirmed round 6; the promotion cascade is bounded by the skipped cap, pinned by test); release-strictly-after-delivery carries two further documented exceptions beside the degraded path — the coordinator-bypassing fast result (releases via a jobId-filtered call from the message job-result handler) and the deadline release (overlaps the awaited generation). Per-message memory, per-author incognito, the ownership guard (history row role + persona must match the skipped author), and per-item error isolation on both the build and store loops all shipped. Residuals ride the tracker tasks filed 2026-11-19 (phantom-cycle teardown on refused fan-outs, shutdown races, cap-trim ordering, header/comment consistency sweep) and the TASK-1457/TASK-1458 folds.
