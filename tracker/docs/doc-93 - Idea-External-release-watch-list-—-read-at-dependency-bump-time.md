### Idea: External-release watch list — read at dependency-bump time

_Focus: five watches that fire on something outside this repo — an upstream release, a provider catalog change, or a sighting in live data — collected as one list to read at the moment Dependabot creates._

## Why one doc

Each member fires on an event no query over our own code can surface: a library release, a provider's model list changing, or a message shape appearing in live traffic. A tracker task's whole value is being findable by an `area`/`size`/`state` query at selection time, and none of these is reachable that way — so five pool slots buy nothing that one list does not.

The real gain is concrete rather than tidy: **TASK-93 and TASK-119 both fire on "next dependency bump," which is a moment Dependabot creates weekly.** One doc read at that moment beats two rows nobody queries. Read this list during the release security-preflight and whenever a Dependabot PR for one of the named packages lands.

**Selection cost: low.** Nothing here was ever going to be picked by a drain query.

## Members

- **TASK-93 — `@discordjs/rest` REST queue stall under sustained rate-limit pressure** (filed 2026-05, was state:observable size:M). The root cause of the voice-transcription hang fixed in PR #1000 was `await channel.sendTyping()` blocking forever when discord.js's REST queue stalled; the PR's fire-and-forget plus ESLint guard prevents whole-pipeline hangs, but the queue stall itself is unexplained upstream behavior. Investigation shape: (a) reproduce by hammering `sendTyping` against one channel under rate-limit pressure; (b) structured logging around `RequestManager` queue depth and retry counts; (c) check `@discordjs/rest@2.7.x` changelogs for queue-stall fixes; (d) decide upgrade vs. a `Promise.race` timeout helper for all REST calls. Trigger/cost: deferred on blast radius — it touches every REST call pattern, not just `sendTyping`. Fires on another hang of the same class against a different endpoint, OR opportunistically at the next discord.js bump. Evidence 2026-09-04: `grep -n "^  '@discordjs/rest@" pnpm-lock.yaml` → only `2.6.3` resolved (one patch above the title's 2.6.1, not the 2.7.x the fix shape names); `grep discord.js services/bot-client/package.json` → `^14.27.0`, unbumped.
- **TASK-119 — Drop the `qs` pnpm override when express/supertest ship it upstream** (filed 2026-05, was state:observable size:S). PR #1088 added a root `pnpm.overrides` entry for `qs` to clear GHSA-q8mj-m7cp-5q26; the override is transient and can be deleted once express and supertest depend on a fixed `qs` directly. Fix shape: `pnpm why qs` shows current consumers — when both report the fixed version as a direct dep rather than via the override, delete the override line and re-run `pnpm install`. Trigger/cost: fires when Dependabot opens a follow-up bumping express or supertest, or at the next dep-audit pass; the cost of leaving it is a stale line in `package.json`, nothing more. Evidence 2026-09-04: `grep -n '"qs"' package.json` → override present, and **actively maintained rather than gone stale** — it now reads `qs@<6.16.0 → >=6.16.0 <7.0.0`, a newer floor than the PR's original `>=6.11.1 <6.15.2` clause; `grep -n "^  qs@" pnpm-lock.yaml` → resolves through the override to `6.16.0`, not via a direct express/supertest dep.
- **TASK-394 — A transformers.js major could silently stop the embedding overflow warn** (filed 2026-08, was state:observable size:S). `countInputTokens` in `packages/embeddings/src/embeddingWorker.ts` calls `tokenizer(text)` synchronously and reads `encoded.input_ids.dims`; if `@huggingface/transformers` ever makes the tokenizer async, the call returns a Promise, `input_ids` is `undefined`, and the function degrades to `undefined` — the SAFE direction, but the overflow warn silently stops firing. Fix shape when the trigger fires: re-run the tokenizer shape probe (call `p.tokenizer(text)` on a deliberately over-long input, confirm `input_ids.dims` is still `[1, N]` with N past 512) and await it if it went async. About a minute of work. Trigger/cost: a `@huggingface/transformers` MAJOR bump (Dependabot will PR it), OR prod ceasing to emit `Input exceeded the model window` despite long queries still being assembled. Cost of missing it: the warn goes quiet, which reads as "no overflow" — the same silence the original PR existed to remove. **Recorded decision — do not "fix" this preemptively**: no test was added because a mocked-async-tokenizer test would assert degradation to `undefined`, which is both the current AND the broken behaviour, so it would pass either way; and no defensive thenable check was added because the whole counting path is deliberately fail-soft. Evidence 2026-09-04: the task's own reasoning is the evidence; the trigger is externally dated and has not fired.
- **TASK-163 — Confirm TupperBox's applicationId against a real proxied message** (filed 2026-06, was state:observable size:S). `KNOWN_PROXY_APP_IDS` (`packages/common-types/src/constants/proxyBots.ts`) lists TupperBox on an operator-confirmed public-app-id basis, not on an observation in our own data. Confirm shape: capture a real TupperBox-proxied reference's `applicationId` via log or probe and verify it equals the constant. Trigger/cost: fires when a TupperBox user is available to test, or a TupperBox-proxied message appears in logs. Safe failure mode — a wrong id degrades a TupperBox-proxied human to `role="bot"` (reads as automation rather than the person addressed), NOT self-reply confusion, which would need `assistant`. **Weak member**: nothing breaks or is noticed until a TupperBox user is actually seen. Evidence 2026-09-04: `git grep -n "431544605209788416" packages/common-types/src/constants/proxyBots.ts` → the comment still says "operator-confirmed public app id", not "observed in our data"; `git log --oneline --grep="TupperBox"` → only the introducing commit, no later confirmation.
- **TASK-806 — `ZAI_MODEL_CATALOG` is hand-curated with no sync mechanism** (filed 2026-08, was state:ready size:S). The catalog lives in `packages/common-types/src/constants/ai.ts` (`ZAI_MODEL_CATALOG`, read at `ai.ts:616`); every new z.ai model needs a manual entry, and a missing entry silently degrades routing and capability checks. Options to evaluate: (a) an authenticated periodic probe comparing `/models` ids against catalog keys, warn-only, in the weekly ops health sweep; (b) a release-checklist line; (c) accept hand-curation and document the update path next to the constant. Acceptance: one option chosen and implemented (or explicitly ruled out with the reason), and the constant carrying a comment naming how it stays current. **Recorded probe result (2026-08-27, owner-asked)**: z.ai's `/models` endpoint EXISTS but is 401-gated behind auth and returns no syncable metadata — no vision or context-length fields — so the catalog stays hand-curated regardless of which option wins; option (a) can only compare ids. Trigger/cost: `glm-5.3-flash` was the triggering miss; this is the odd member of the doc in that it is `state:ready` rather than externally gated — the external part is only the catalog's drift, not the work. Evidence 2026-09-04: `git log --oneline -S "Source of truth for membership: docs.z.ai" -- packages/common-types/src/constants/ai.ts` → `a95ca851a`, 2026-06-14, i.e. the existing source-of-truth comment predates the task's filing by 2.5 months and was already judged insufficient; `git grep -n "ZAI_MODEL_CATALOG" packages/tooling/src/health/*.ts docs/reference/tooling/` → no periodic-probe or release-checklist hit.
