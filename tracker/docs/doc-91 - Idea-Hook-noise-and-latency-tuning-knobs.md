### Idea: Hook noise and latency tuning knobs

_Focus: five process-hook watches that name no defect — each says "if this proves noisy or slow, tune it," and the signal arrives to whoever feels the noise, never to a query._

## Why one doc

None of these is a defect. Each is a tuning knob on a hook that works: a trigger regex that might over-fire, a loop that might get slow, an ordering artifact that might confuse a future contributor. The signal they wait on is felt, not queried — it reaches whoever is annoyed by the banner or the latency, which is never a `state:ready size:S` selection pass. Five tuning knobs in one doc is the honest shape; five pool slots is not. Companion to doc-90, which holds the same layer's actual defects.

**Selection cost: none.** No query would surface any of these at the moment the noise is felt, so nothing is lost by consolidating them.

- **TASK-237 — `pnpm quality` at pre-commit can disagree with the lint-staged hook** (filed 2026-07, was state:observable size:S). lint-staged runs `prettier --write` BEFORE `eslint`, so it lints prettier-EXPANDED code; a manual `pnpm quality` before committing lints the compact as-written source, so a function near `max-lines-per-function` can pass quality yet fail the hook once prettier wraps it (proven: a 94-line fn → 103 lines post-prettier). Fix shape: either (a) do nothing, or (b) a one-line doc note that the hook is authoritative on formatting-sensitive rules. Trigger/cost: **explicitly benign** — not a gate hole. Once the expanded code is committed, CI lints the same form and the pre-commit hook catches it first; the only surprise is a manual pre-commit `pnpm quality` on unformatted source, so the sole unclaimed value is the doc note. The original "cwd config divergence / CI is the lenient side" framing was investigated and DISPROVEN the same day (2026-07-08) — do not re-derive it. Evidence 2026-09-04: `git grep -rn "lint-staged.*authoritative\|authoritative.*formatting" .claude/ docs/` → no match, so option (b) was never taken; `.husky/pre-commit` still runs `npx lint-staged` with prettier before eslint.
- **TASK-287 — `eslint-on-edit.sh` runs a synchronous `pnpm exec eslint` per TS edit** (filed 2026-07, was state:observable size:S). Fix shape: debounce by file+mtime. `--cache` is **RULED OUT and must not be re-attempted** — measured 2026-07-24 and disproved, because ESLint's cache is keyed on the linted TARGET and this hook only ever lints the file just edited, so the entry is always stale (4839/4787/4707ms without vs 4778/4899/4795ms with); it was added on that basis, reverted in #1783, and the hook now carries a comment saying so. Trigger/cost: **currently MOOT — the hook is not registered in `.claude/settings.json`**, so the ~4.8s per edited `.ts` file is not being paid at all; its output went to a PostToolUse channel that never reached the agent (TASK-458). Promote only if it is ever re-registered on evidence that the delivery channel changed. **Prior-close note**: a prior pass deliberately declined to archive this pending possible re-registration; on the merits it is arguably an admission-bar rule-out (a hypothetical cost of an unregistered hook), but reversing that prior close is the owner's call, not an agent's — it is carried here rather than archived for exactly that reason. Evidence 2026-09-04: `git grep -n "eslint-on-edit" .claude/settings.json` → no match.
- **TASK-307 — Watch the bug-remediation first-fix trigger for over-firing** (filed 2026-07, was state:observable size:S). Trigger/cost: a too-eager nudge trains skim-past, which defeats the nudge; promote when the banner visibly over-fires on non-remediation prompts. No over-firing evidence has been logged anywhere. Evidence 2026-09-04: `grep -n "delete|edit|create|browse|view" .claude/hooks/skill-eval.sh` → the same alternation is still live.
- **TASK-600 — Cap the skill-eval address clause loop if submit latency becomes noticeable** (filed 2026-08, was state:observable size:S). `skill-eval.sh` runs synchronously on every UserPromptSubmit, and its address branch forks two greps PER CLAUSE with no cap on clause count. Fix shape: break after N clauses (40 is roughly 2× the measured worst case) and note in the comment that the tail past the cap is unexamined — a miss costs one absent suggestion, the same cost model the branch already documents for its five accepted gaps. Trigger/cost: measured on this machine at ~97ms typical, ~213ms worst case at 20 clauses, roughly linear in clause count; a whole-prompt grep for "address" gates entry, so prompts without the word pay nothing. Promote when prompt submission feels laggy on a long paste, or someone times the hook past ~500ms. Evidence 2026-09-04: `grep -n "MAX_CLAUSE\|break" .claude/hooks/skill-eval.sh` → no clause-count cap constant; the `while` loop at line 227 has no upper bound.
