### Idea: Config-service and config-schema refactor family

_Focus: six mutually entangled items over `LlmConfigService`/`TtsConfigService` and the config schema they read — each one changes where the others land, so they are scoped together or not at all._

## Why one doc

One subsystem, and the members are **mutually entangled** rather than merely adjacent: TASK-90's query/mutation split changes where TASK-89's invalidation hooks go, and TASK-113's NOT NULL tightening removes the `?? fallback` branches TASK-48's type consolidation would otherwise have to model twice. Picking one alone re-opens the others, which is the same argument doc-18 Phase 1 makes about its own spine.

Checked and rejected as owners: **doc-15** (Preset Cascade Standardization) is cross-tier preset *UX*, not service internals; **doc-9** (Model Configuration Overhaul) closed 2026-07-01.

**Selection cost: low** — but see Phase 0, which must not wait on the refactor.

## Phase 0 — TASK-362, mechanically fixable today

**TASK-362 is the odd member and should ship on its own, ahead of everything else here.** It is not entangled with the refactor, it has clear precedent already written down in `prisma/drift-ignore.json`, and it is a one-migration change — naming it Phase 0 is what stops the consolidation from parking it behind a design pass it does not need. Its bullet is in the Members list below.

## Members

- **TASK-362 — `system_prompts.isDefault` has no partial unique index** (filed 2026-07, was state:ready size:S). **Phase 0 — do this first, independently.** `system_prompts` has no constraint preventing two rows with `isDefault: true`, unlike `llm_configs` and `tts_configs`, which both carry partial unique indexes for exactly this (`llm_configs_default_unique`, `tts_configs_free_default_unique` — see `03-database.md` § Protected Indexes). Every reader uses `findFirst({ where: { isDefault: true } })` with **no `orderBy`**, so with two default rows the one returned is whatever the planner picks first, unstable across queries and deploys. Fix shape: a partial unique index `WHERE is_default = true`, mirroring the llm/tts pattern — and it **must** go in `prisma/drift-ignore.json`'s `ignorePatterns`, because Prisma cannot represent partial unique indexes and will try to DROP it on every subsequent migration, which is precisely why the existing entries are listed there. Trigger/cost: pre-existing and not introduced by #1873, but #1873 added a third reader (`DescriptionPromptService`) whose picked row frames **every image description the instance writes** — so an unstable pick is an unstable framing. The reader marked this row **owner-call: yes** for that reason. Promote when a second `isDefault` row is observed in any environment, OR the next migration touching `system_prompts` for another reason (the index is cheap to add while already editing that table). Evidence 2026-09-04: `sed -n '314,326p' prisma/schema.prisma` → plain `@@index([isDefault])`, not partial-unique; `grep -n "system_prompts" prisma/drift-ignore.json` → no hits.
- **TASK-89 — Smart per-user cache invalidation for LLM + TTS configs** (filed 2026-05, was state:observable size:M). `LlmConfigService.invalidateCacheSafely()` and its `TtsConfigService` mirror both call `cacheInvalidation.invalidateAll()` on every mutation, nuking every user's TTLCache; the better pattern, `ConfigCascadeCacheInvalidationService`, already exists but is unwired. Fix shape: upgrade BOTH services together — enumerate affected users, publish per-user events, and fall back to invalidate-all only for unenumerable changes such as `setAsFreeDefault`. ~200–300 LOC across both services plus tests. Trigger/cost: opportunistic on the next touch of either config service, OR if unconditional invalidation produces measurable cache-thrash in production. **Entanglement**: where these hooks land depends on TASK-90's split, so sequence them together. Evidence 2026-09-04: `git grep -n "invalidateAll()\|ConfigCascadeCacheInvalidationService" packages/cache-invalidation` → the service exists with its own class and tests but is not referenced from either config service.
- **TASK-90 — Split `LlmConfigService` + `TtsConfigService` into query/mutation/cache** (filed 2026-05, was state:observable size:L). Council recommended pre-splitting; the owner chose mirror-as-single-file and to split BOTH later when the burden became real. Fix shape: when either crosses the lint threshold, split BOTH into `*QueryService.ts` + `*MutationService.ts` (cache wiring stays in mutation), mirrored for LLM and TTS in the same PR for symmetry. **Trigger measurably UNFIRED**: the task's own promote-when is "ESLint `max-lines` flags either service," and it does not. Evidence 2026-09-04, measured with the counted-lines technique from `02-code-standards.md` (`npx eslint <file> --rule '{"max-lines":["error",{"max":1,"skipBlankLines":true,"skipComments":true}]}'`): `LlmConfigService.ts` → **337** counted lines, `TtsConfigService.ts` → **365** — both under the 400 error threshold. The task's "~600+ raw LOC" framing is raw `wc -l`, which is not the metric.
- **TASK-48 — LLM config type consolidation (`Resolved`/`Mapped`, `Database`/`Raw`)** (filed 2026-06, was state:ready size:M). `ResolvedLlmConfig` (`common-types/types/configResolution.ts`) is `MappedLlmConfig` (`common-types/services/LlmConfigMapper.ts`) minus `{ provider }`, yet both independently `extends ConvertedLlmParams` and re-list the same seven DB fields, so the kinship is implicit and the two can silently drift; separately, `DatabaseLlmConfig` (`identity/PersonalityValidator.ts`) and `RawLlmConfigFromDb` may overlap. Fix shape: express `ResolvedLlmConfig` as `Omit<MappedLlmConfig, 'provider'>` (or a shared base) so the relationship cannot drift, and audit whether the two raw shapes unify. Trigger/cost: cosmetic/cognitive debt, not behavioral — the field difference IS intentional (provider stays on the personality seed) — so it deserves its own diff with its own review, because it touches load-bearing mapper/resolver types. **Explicit non-target**: the Mapped/Resolved/Loaded × Llm/Tts/Vision/Stt breadth is a deliberate per-axis-concrete choice; only the within-axis near-duplication is in scope. **Entanglement**: TASK-113 removes `?? fallback` branches this consolidation would otherwise model twice. Evidence 2026-09-04: `git grep -n "interface ResolvedLlmConfig\|interface MappedLlmConfig" packages/common-types` → two separate, unrelated `extends ConvertedLlmParams` declarations at `configResolution.ts:43` and `LlmConfigMapper.ts:85`.
- **TASK-113 — Tighten `default_llm_config_id` / `default_tts_config_id` to NOT NULL** (filed 2026-05, was state:ready size:M). Both columns are `String?` and predate Phase 5b's atomic user-creation work, which made `default_persona_id` NOT NULL; users are now created via a deterministic CTE that has access to system free-defaults, so both could be backfilled and tightened. Fix shape: (a) migration backfilling NULL rows with the system free-default config id; (b) `ALTER COLUMN ... SET NOT NULL`; (c) drop the `?` in `schema.prisma`; (d) audit resolver code and delete the no-longer-reachable null branches. ~50–80 LOC plus a migration. Trigger/cost: **no bug today** — the resolvers handle null correctly and the cascade design tolerates user-tier null gracefully; this is for invariant clarity and dead-code removal. Promote at the next user-identity audit, or if a config-cascade bug ever traces to ambiguous null semantics. **Entanglement**: this is the member that shrinks TASK-48's surface. Evidence 2026-09-04: `grep -n "defaultLlmConfigId\|defaultTtsConfigId" prisma/schema.prisma` → both still declared `String?`.
- **TASK-186 — AdminSettings default pointers: 4 FK columns → junction table** (filed 2026-06, was state:dependent size:M). P3-S3 stores the global/free default config pointers as four nullable FK columns on the `AdminSettings` singleton (`{global,free}Default{Llm,Vision}ConfigId`) — councilled (GLM-5.2 / Kimi-K2.7 / Qwen-3.7-max) and chosen on **YAGNI** grounds, matching the existing per-slot-FK pattern; Qwen's dissent favoured a normalized `DefaultLlmConfig(tier, slot) → configId` junction table for extensibility. Fix shape: migrate the FK columns to a junction table with `@@id([tier, slot])` and `onDelete: SetNull`; the resolver becomes one `findMany` → `Record<Tier, Record<Slot, Config>>`. Trigger/cost: promote when the default slot or tier count grows beyond 2×2 — e.g. an audio or embeddings slot, or a premium/beta tier. **Recorded owner framing**: the owner was swayed by YAGNI and flagged this for revisit, so the row exists to make that revisit possible, not to relitigate the original call. Evidence 2026-09-04: `grep -n "DefaultLlmConfigId\|DefaultVisionConfigId" prisma/schema.prisma` → exactly the four columns, no growth.
