### Theme: PGLite Fidelity + Real-Postgres Integration Tier

_Focus: close the component-tier fidelity gap — harvest the remaining DDL the shared PGLite schema misses, provision real Postgres for the integration tier, then test the behaviors PGLite structurally cannot model (trigger→NOTIFY, concurrency/locking, pg.Pool)._

Anchored by the PGLite-fidelity audit (2026-06-27, during the vision-config epic) plus the Test-Pyramid epic's Phase-4 CI cleanup (#1346/#1347). Three flat follow-up rows consolidated here 2026-07-02 (granularity-ladder re-org): one independent schema-generator cleanup (Phase 1), and a two-step dependency chain — provision Postgres (Phase 2) → write the real-Postgres tests PGLite can't host (Phase 3).

### Phase 1 — Promote DEFERRABLE-FK harvesting to the shared PGLite schema generator — ✅ SHIPPED (#1458, 2026-07-02)

The generator's third harvester (`extractDeferrableConstraints`) merges the `ALTER CONSTRAINT ... DEFERRABLE` statements into `pglite-schema.sql` (all six: 4 circular + TTS default + vision default), with last-wins dedup treating BOTH a `NOT DEFERRABLE` revert and a `DROP CONSTRAINT` as retirements (mirrors Prisma's DROP+re-ADD losing deferrability). The per-file parse + last-wins scaffolding unified into a regex-parameterized kernel shared by all three harvesters. The bespoke workaround turned out to live in TWO component tests (DatabaseSyncService + alignTtsGlobalsRecovery — five loaders total); both dropped their migration replays. The deferrability invariant lives on through the sync suites' atomic circular-insert tests, which fail if a future migration drops a clause. One latent-assumption follow-up filed (tracker task: harvester dedup keys on bare name, not (table, name)).

### Phase 3 — Real-Postgres integration tests: trigger→NOTIFY cache-invalidation chain + concurrency + pool behaviors

A PGLite-fidelity audit (2026-06-27) found the behaviors PGLite structurally CAN'T model (vs. the schema-DDL gaps the harvester closes): (1) the `pg_notify` cache-invalidation **triggers + functions** (`notify_*_cache_invalidation()`) — the trigger→NOTIFY→`DatabaseNotificationListener`→cache-clear chain only works against real Postgres (PGLite is single-connection, no cross-connection LISTEN/NOTIFY); the listener's own side is unit-tested with mocks but the DB-trigger half isn't; (2) **concurrency/locking** — `SELECT FOR UPDATE`, advisory locks, serialization/deadlock, concurrent-upsert/`ON CONFLICT` races, MVCC-under-contention; (3) **`pg.Pool`** saturation / acquisition-timeout / the `DATABASE_POOL_STATS` gauge. Also low-value: prod's approximate IVFFlat **recall** behavior (PGLite seqscans → exact, so it can't surface a real match the index would miss). **Fix shape**: once the integration tier has real Postgres (Phase 2 above), add tests for the trigger/NOTIFY chain + the highest-risk concurrency path first. **Promote when**: the real-Postgres integration tier is stood up, OR a prod incident traces to one of these untested behaviors. Surfaced 2026-06-27 (PGLite-fidelity audit during vision-config epic).

**Premise correction 2026-08-28** (found while grounding the Phase 2+3 build; the audit's original wording said the triggers "are absent from PGLite", which is no longer true and has been struck above): the function and all four triggers ARE present in `packages/test-utils/schema/pglite-schema.sql` (harvested from the migrations — Prisma's own diffing cannot see functions or triggers at all). The schema's own comment states their `pg_notify` calls are "listener-less no-ops under PGLite". So the gap is narrower and better-defined than the audit claimed: the trigger FIRES under PGLite, but nothing can observe the NOTIFY, because delivery needs a second connection. What real Postgres buys is observability of the delivery, not existence of the trigger — and the test must therefore write from a SEPARATE connection from the one that LISTENs, or it proves nothing PGLite couldn't have.

Second correction, same grounding pass: the live definition of `notify_personality_cache_invalidation()` is the THIRD one — `prisma/migrations/20251119231105_optimize_cache_invalidation_for_llm_configs/`. The two earlier migrations (`20251119154500`, `20251119211218_fix_llm_config_cache_invalidation_trigger`) are superseded, and the FIRST one contains a real defect (two consecutive `SELECT ... INTO personality_ids` where the second silently overwrites the first) that was fixed in Nov 2025. Assert against the live file only; the earliest one describes behavior that has not existed for nine months.
